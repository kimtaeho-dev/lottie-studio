# 렌더러 제약: Skottie 미리보기 vs lottie-web 프로덕션

이 스튜디오의 미리보기는 **Skia Skottie(CanvasKit)** 이고, 우리 프로덕션 재생은
**lottie-web 5.x SVG 렌더러** 다. 두 엔진의 지원 범위는 완전히 겹치지 않는다.
그래서 미리보기에서 멀쩡한 씬이 프로덕션에서 조용히 깨질 수 있다.

이 문서는 그 간극을 씬 작성 단계에서 막기 위한 규칙이다. 기계로 검사할 수 있는
부분은 스캐너가 강제한다:

```bash
npm run check:lottie
# 또는
node scripts/check-lottie-web-compat.mjs [--max-kb N] <lottie.json...>
```

BLOCK 이 하나라도 남아 있으면 스캐너가 종료 코드 1 로 실패한다. 눈으로 봐야
하는 부분은 `/compare.html` 에서 두 렌더러를 나란히 놓고 확인한다.

---

## BLOCK — 반드시 없애야 한다

### `ty:"mm"` — 머지 패스

- **왜**: Skottie 는 머지 패스를 렌더하지만 lottie-web SVG 렌더러는 **무시한다**.
  미리보기에서는 합쳐진 도형이 보이고, 프로덕션에서는 합치기 전의 원본 패스가
  그대로 겹쳐 나온다. 도형이 깨진 채 배포된다.
- **대안**: 도형을 디자인 툴에서 미리 하나의 패스로 합쳐 단일 `ty:"sh"` 로
  내보낸다. 구멍(도넛 등)은 머지 패스 대신 같은 그룹 안에서 fill-rule 로
  처리한다 — `ty:"fl"` 의 `r` 에 `2`(even-odd)를 주면 겹친 부분이 뚫린다.

### 문자열 `x` 속성 — 표현식

- **왜**: Skottie 는 표현식을 **평가하지 않는다**. lottie-web 은 (표현식 빌드에
  한해) 평가한다. 즉 미리보기에서는 표현식이 없는 것처럼 보이고 프로덕션에서만
  값이 움직이거나, 그 반대가 된다. 두 화면이 조용히 갈린다.
- **대안**: 표현식을 없애고 결과를 **키프레임으로 굽는다**. 반복 회전 같은
  주기 동작은 선형 키프레임 두 개로, 랜덤/노이즈는 실제 키프레임 시퀀스로
  대체한다.
- 숫자나 배열인 `x`(키프레임 이징 `i`/`o`의 `x`, 분리된 위치의 x축)는 정상이다.
  스캐너도 `x` 가 **문자열일 때만** 잡는다.

### 비어있지 않은 `ef` 배열 — 레이어 이펙트

- **왜**: 두 렌더러의 이펙트 지원 집합이 서로 다르다. 어느 한쪽만 그리거나,
  둘 다 그리되 결과가 다르다. 어느 쪽인지는 이펙트마다 다르므로 통째로 막는다.
- **대안**: 이펙트를 셰이프로 재구성한다.
  - 드롭 섀도우 → 오프셋한 복제 레이어에 어두운 단색 + 낮은 불투명도
  - 글로우 → 방사형 그라디언트(`gf`) 레이어를 뒤에 깐다
  - 틴트/필 → 셰이프의 `fl` 색을 직접 바꾼다
  - 블러 → 미리 렌더한 이미지 에셋으로 대체하거나 디자인에서 제거한다

### `ty:5` — 네이티브 텍스트 레이어

- **왜**: Skottie 는 씬 폴더에 동봉한 폰트 파일을 SkFontMgr 에 올려 폰트의
  **내장 패밀리 이름**으로 해석한다. lottie-web 은 CSS `@font-face` 로 브라우저
  폰트 스택에 의존한다. 셰이핑 주체가 아예 달라서 자간, 베이스라인, 줄바꿈
  위치가 다르게 잡힌다. 폰트가 로드되지 않으면 lottie-web 은 **에러 없이**
  시스템 폰트로 폴백하기까지 한다.
- **대안**: 글리프를 **아웃라인으로 변환**해서 `ty:"sh"` 셰이프 텍스트로
  내보낸다. 렌더링 결과가 폰트 환경과 무관해지므로 두 엔진이 같은 픽셀을 낸다.
- **대가를 알고 쓸 것**: 아웃라인으로 바꾸면 텍스트 슬롯 편집(속성 패널에서
  카피를 고치는 기능)을 잃는다. 프로덕션 에셋에서는 이 교환이 옳다 — 편집
  가능성보다 두 엔진에서 같게 보이는 것이 우선이다. 카피가 자주 바뀌는
  씬이라면 문구 확정 후 마지막 단계에서 아웃라인으로 굽는다.

### 최상위 `v` `fr` `ip` `op` `w` `h` `layers` 누락

- **왜**: 플레이어 계약 위반이다. 로더가 크기나 프레임 범위를 계산하지 못해
  로드 자체가 불안정해진다.
- **대안**: 전부 채운다. `op` 는 exclusive 로 다룬다(마지막 프레임은 `op - 1`).

### JSON 파싱 실패

- **왜**: 두 렌더러 모두 씬을 열지 못한다.
- **대안**: 고친다. 저장 직후 `node -e "JSON.parse(...)"` 로 확인하는 습관.

### 용량 초과 (기본 150KB)

- **왜**: 프로덕션 번들에 그대로 실린다. 아래 "예산" 참고.

### 키프레임 이징(o/i)이 한쪽에만 있음

- **왜**: lottie-web 은 한 구간의 이징을 **그 구간을 시작하는 키프레임 객체 하나**에서
  `o`(out)와 `i`(in)를 함께 읽는다(`keyData.o`, `keyData.i` — 다음 키프레임의 값은
  아예 읽지 않는다). `o`만 있고 `i`가 없으면(또는 그 반대) `undefined.x`에
  접근하면서 그 구간의 애니메이션이 깨진다. Skottie는 관대하게 넘어가서 미리보기는
  멀쩡한데 프로덕션에서만 도형이 사라지거나 잘못된 값으로 튄다. 특히 3개 이상
  키프레임을 이어붙일 때 "이 구간 나가는 `o`는 여기, 저 구간에서 들어오는 `i`는
  다음 키프레임에" 식으로 나눠 쓰기 쉬운데, 그게 정확히 이 버그다.
- **대안**: 한 구간의 `o`와 `i`를 **항상 그 구간을 시작하는 키프레임에 함께** 쓴다.
  마지막 키프레임에는 `o`/`i` 둘 다 넣지 않는다(아무 구간도 시작하지 않으므로).
  중간 키프레임은 "이전 구간의 `i`"와 "다음 구간의 `o`"를 **둘 다 자기 자신에게**
  가진다 — 이전 구간 몫의 `i`를 다음 키프레임으로 미루면 안 된다. 스캐너가
  `LW-KEYFRAME-EASING-SPLIT` 로 이 패턴을 자동으로 잡는다.

### 마스크(`masksProperties`)에 `x`(페더) 필드가 없음

- **왜**: lottie-web 의 마스크 생성 코드가 `x.k`를 조건 없이 바로 읽는다.
  `x` 필드 자체가 없으면 그 자리에서 예외가 나고 해당 레이어를 통째로 그리지
  않는다. Skottie는 `x` 없이도 문제없이 렌더한다.
- **대안**: 마스크를 쓸 거면 `"x": { "a": 0, "k": 0 }` 를 항상 같이 넣는다.

## WARN — 통과하지만 `/compare.html` 에서 반드시 눈으로 볼 것

WARN 은 스캐너를 실패시키지 않는다. 두 렌더러가 **다르게 그릴 수 있는** 구간을
표시하는 것이므로, 하나라도 뜨면 비교 페이지에서 해당 프레임을 직접 확인한다.

### `ddd:1` — 3D 레이어

- **왜**: Skottie 는 실제 3D 변환을 한다. lottie-web SVG 는 2D 평면에서 흉내만
  낸다. 레이어가 z축으로 교차하면 **겹침 순서가 달라진다**.
- **대안**: 2D 로 평탄화하고 깊이감은 스케일·불투명도·블러 대체 셰이프로 만든다.
  겹침 순서는 레이어 순서로 명시적으로 정한다.

### `bm` 이 0이 아님 — 블렌드 모드

- **왜**: lottie-web 은 CSS `mix-blend-mode` 로 매핑한다. CSS 블렌딩의 합성
  대상은 **스태킹 컨텍스트**라서, After Effects/Skottie 가 합성하는 대상과
  달라질 수 있다. 특히 매트나 3D 와 섞이면 결과가 갈린다.
- **대안**: 블렌드 결과를 미리 합성해 단일 셰이프/이미지로 굽거나, 일반 알파
  합성으로 디자인을 다시 잡는다.

### `tt` — 트랙 매트

- **왜**: 알파 매트는 비교적 잘 맞지만 **루마 매트**는 두 엔진의 휘도 계산과
  전처리가 달라 가장자리와 중간 톤이 다르게 나온다.
- **대안**: 가능하면 루마 매트를 알파 매트로 바꾼다. 그라디언트 페이드가
  필요하면 매트 레이어를 알파 그라디언트로 만들어 알파 매트를 쓴다. 단순한
  사각/원형 클리핑이면 마스크보다 `rc`/`el`의 크기·위치 키프레임으로 대체하는
  편이 안전하다 — 마스크의 손으로 만든 패스는 그 자체로 별도 WARN 항목이다.

### `st`/`gs` 의 `d` 배열 — 대시 스트로크

- **왜**: lottie-web 의 대시 스트로크에 알려진 이슈가 있다. 대시 오프셋
  애니메이션과 패스 시작점 처리에서 어긋난다.
- **대안**: 대시 행진 효과는 **단일 트림 패스**로 표현한다. 정적인 점선이라면
  대시를 실제 도형(짧은 선분들)으로 구워 넣는다.

### 한 `it` 그룹 안에 `ty:"tm"` 2개 이상 — 다중 트림 패스

- **왜**: 트림 패스를 여러 개 쌓았을 때의 적용 순서 해석이 두 엔진에서 다르다.
- **대안**: 그룹을 나눠 트림 패스를 하나씩만 둔다. 한 패스에 두 구간이
  필요하면 패스를 복제해 각각 하나의 트림으로 처리한다.

### 마스크(`masksProperties`)에 손으로 만든 베지어 패스

- **왜**: lottie-web 의 마스크 렌더러(`mask.js`)는 정점의 `i`/`o` 베지어 핸들을
  **정점 기준 상대좌표가 아니라 그 자체로 절대좌표**처럼 SVG `C` 커맨드에 바로
  꽂아 넣는다. Skottie 와 일반 셰이프 프로퍼티는 표준대로 상대좌표로 해석한다.
  그래서 직선 구간을 의도한 `i:[0,0], o:[0,0]`(상대 0 — 정점 자신) 같은 값이
  Skottie 에서는 맞게 나오고 lottie-web 에서는 도형이 원점 쪽으로 뒤틀려 나온다.
  반대로 lottie-web 기준으로 맞춘 값(핸들 = 정점 좌표 그대로)은 Skottie 에서
  뒤틀린다. 즉 **두 엔진을 동시에 만족시키는 값이 존재하지 않는다.**
- **대안**: 직선 위주의 클리핑/리빌이면 마스크 대신 `rc`(사각형)나
  `el`(원)의 크기(`s`)·위치(`p`) 자체를 키프레임으로 움직여 만든다 — 두
  렌더러 모두 이 표준 프로퍼티 보간은 동일하게 처리한다. 곡선 마스크가
  꼭 필요하면 `/compare.html` 로 양쪽을 반드시 확인한다.

## 안전 목록 — 양쪽에서 동일하게 동작한다

아래는 두 렌더러가 같은 결과를 내므로 마음 놓고 쓴다.

- **도형 레이어**(`ty:4`)와 그 안의 `sh` / `rc` / `el` / `sr` / `fl` / `st`
- **셰이프 그라디언트** `gf`(그라디언트 필), `gs`(그라디언트 스트로크) —
  단 `gs` 에 대시(`d`)를 붙이면 WARN 이다
- **리피터**(`ty:"rp"`)
- **프리컴프**(`ty:0` + `assets[].layers`)
- **타임 리맵**(`tm` 프로퍼티)
- **이미지 에셋**(외부 파일 참조)
- **단일 트림 패스**(한 그룹에 `ty:"tm"` 하나)
- **마스크**(`masksProperties`) — 단, `x`(페더) 필드를 반드시 넣고, 손으로
  만든 베지어 패스는 안전 목록이 아니다(WARN 항목 참고)

여기에 표현식·이펙트·머지 패스를 섞지 않는 한, 이 조합만으로 대부분의
프로덕션 씬을 만들 수 있다.

## 예산

- **씬당 150KB 이하.** 스캐너 기본값이며 `--max-kb` 로 조정할 수 있지만,
  올리기 전에 먼저 줄일 방법을 찾는다.
- **이미지는 base64 인라인(`e:1`)이 아니라 외부 파일로.** 인라인은 base64
  때문에 원본보다 약 33% 커지고, 그 용량이 JSON 파싱 비용으로 그대로 돌아온다.
  이미지 파일을 `lottie.json` 옆에 두고 `assets[].p` 에 파일명만 적는다.
  Skottie 는 named-blob 맵의 키로, lottie-web 은 `assetsPath` 기준 경로로
  같은 파일을 찾는다.
- 키프레임을 과하게 굽지 않는다. 프레임마다 키를 찍는 대신 이징을 쓴다.

## 완료 조건

아래를 **순서대로** 통과해야 씬이 끝난 것이다.

1. **JSON 검증**

   ```bash
   node -e "JSON.parse(require('fs').readFileSync('public/projects/<project>/<scene-N>/lottie.json','utf8'))"
   ```

2. **스캐너 통과 — BLOCK 0개**

   ```bash
   node scripts/check-lottie-web-compat.mjs public/projects/<project>/<scene-N>/lottie.json
   ```

   종료 코드가 0 이어야 한다. WARN 이 남아 있으면 4번에서 그 항목을 집중해서
   본다.

3. **모션 스무스니스 검사 — 이징 곡선 자체의 결함**

   ```bash
   node scripts/check-motion-smoothness.mjs public/projects/<project>/<scene-N>/lottie.json
   ```

   정지 프레임 몇 개만 보는 걸로는 못 잡는 종류의 버그를 잡는다 — 이징
   베지어의 시간축이 구간 중간에서 멈췄다가(값은 계속 바뀌는 채로) 다시
   가는 경우, 재생 중 그 지점에서 값이 순간적으로 튄다(`travel-balanced`
   가 한 번 이 문제였다). 브라우저 없이 이징 값의 수학적 성질만으로
   판정하므로, 브라우저 자동화를 못 쓰는 환경에서도 돌릴 수 있다.

4. **`/compare.html` 에서 양쪽 패널 확인** (브라우저를 쓸 수 있을 때)

   ```
   /compare.html?src=/projects/<project>/<scene-N>/lottie.json
   ```

   프레임 **`0`**, **중간**, **`op - 1`** 세 지점을 슬라이더로 고정하고 왼쪽
   (Skottie)과 오른쪽(lottie-web)을 **둘 다** 본다. 한쪽만 보는 것은 확인이
   아니다. 정지 프레임 확인이지 재생 확인이 아니므로, 3번의 모션
   스무스니스 검사를 대체하지 않는다 — 둘 다 통과해야 한다.

   > 브라우저 자동화(예: Claude in Chrome 확장)를 쓸 수 없는 환경이면 이
   > 단계는 건너뛰고 1~3번(JSON 검증·호환성 스캐너·모션 스무스니스)만으로
   > 진행한다. 이 셋은 전부 헤드리스로 돌아가니 별도 브라우저 도구가 없어도
   > 대부분의 실수를 잡는다. 다만 색상·레이아웃·타이포그래피처럼 순수
   > 시각적인 판단은 여전히 사람이 직접 플레이어를 열어 확인해야 한다.

5. **차이 원인 제거**

   두 패널이 다르면 그 차이를 없앨 때까지 고친다. "미리보기에서는 괜찮다"는
   완료가 아니다. 차이가 WARN 항목에서 왔다면 위의 대안으로 교체한다.

   > 텍스트가 있는 씬은 판정이 반대다. 두 패널의 글자가 **서로 다르게** 보이면
   > 폰트가 양쪽에 제대로 들어갔다는 뜻이고, **똑같이** 보이면 오히려
   > `@font-face` 주입이 실패해 양쪽 다 시스템 폰트로 폴백했을 가능성이 크다.
   > 비교 페이지의 진단 로그에서 폰트 로드 성공 여부를 확인한다.
   > 애초에 네이티브 텍스트는 BLOCK 이므로, 아웃라인으로 변환하는 것이 정답이다.

6. **배경 정책 확인**

   전면(full-frame) 구성이면 `bgColor` 슬롯을 가진 배경 레이어가 있는지,
   투명이 기본인 산출물(로고·아이콘·로더·오버레이·로워서드·SVG 파생)이면
   실제로 투명한지 확인한다. 비교 페이지의 체커보드 배경으로 알파를 본다.
